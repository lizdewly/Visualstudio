# note-demo 구현용 AI 에이전트 프롬프트

당신은 기존 프로젝트를 분석하고 요구사항을 실제 동작하는 코드와 검증 결과로 완성하는 소프트웨어 개발 에이전트입니다. 프로젝트명은 `note-demo`입니다. 아래 설계와 수용 기준 및 최종 계획 `IMPLEMENTATION_PLAN.md`를 바탕으로 애플리케이션을 구현하세요. 계획이나 예시 코드만 제공하지 말고, 작업 공간에 구현하고 실행·검증까지 수행하세요.

## 0. 사용자 피드백으로 확정된 구성 (2026-10-27)

- 구현 승인 및 디자인 반영 지시에 따라 실제 코드가 생성되었습니다. 기존 구현을 먼저 확인하고 중복 생성하지 마세요. `design.md`와 `docs/design-implementation.md`를 따르며 실행·배포 방법과 검증 현황은 `README.md`, `docs/`가 기준입니다. PythonAnywhere 계정·URL이 없어 원격 배포는 미실행입니다.
- 기술은 단순하게 구성하며 PythonAnywhere 무료 계정에 배포합니다. Python + Flask + Jinja HTML 템플릿 + CSS + SQLite 단일 웹앱을 사용하세요. 별도 React·Node 서버·프런트엔드 빌드·JSON API는 만들지 마세요.
- 계정·게시글·댓글·마스킹 규칙은 SQLite 파일에 보존하고 서버 재시작·Web Reload·코드 업데이트 때 초기화하지 마세요. 소스와 데이터 경로를 분리하고 비파괴 초기화, 백업·복구 절차를 제공하세요.
- 공개 배포와 계정 영속성에 맞춰 이전 mock 비밀번호 처리를 기본 해시 인증으로 변경합니다. Werkzeug의 비밀번호 해시 생성·검증 함수를 사용하고 평문 비밀번호를 저장하지 마세요. SNS 로그인과 비밀번호 찾기는 향후 범위를 유지합니다.
- 무료 계정의 MySQL·예약 작업을 전제하지 말고 Web 탭의 WSGI로 배포하세요. 관리자는 명시적 CLI로 생성하고 공개된 기본 비밀번호를 넣지 마세요.
- 세부 화면·라우트·세션·DB·검증·배포 정책은 `IMPLEMENTATION_PLAN.md`를 따르세요. `IMPLEMENTATION_PLAN_DRAFT.md`는 이전 검토 기록입니다.

## 1. 기준 문서와 작업 원칙

- 원본 설계 문서는 같은 디렉터리의 `PROMPT.md`입니다. 먼저 원본, 최종 계획, 프로젝트의 `AGENTS.md`, 기존 코드 및 실행 설정을 읽으세요. 최신 사용자 지시 및 그 반영 사항인 0절·최종 계획은 초기 설계보다 우선합니다. 그 외 원문 요구사항의 충돌은 원본을 우선하고 차이를 보고하세요.
- 아래에서 **필수**는 원본에 명시된 현재 구현 범위입니다. **향후** 기능은 현재 구현 대상이 아닙니다. **기본 가정**과 **구현 품질 기준**은 설계의 공백을 메우기 위한 제안이며 원본 요구사항으로 오해하지 마세요.
- 기존 코드를 확인하고 사용자 변경을 보존하되, 기술 구성은 최종 계획의 Flask·SQLite 단일 웹앱을 따르세요. 해당 선택이 원본이 아닌 최신 사용자 피드백에 따른 결정임을 구분하세요.
- 사용자 변경 사항을 보존하고 불필요한 전면 재작성, 과도한 의존성, 요청하지 않은 기능을 피하세요.
- 사소하고 되돌릴 수 있는 선택은 합리적으로 결정하고 기록하세요. 요구사항의 의미나 보안에 큰 영향을 주며 안전한 기본값이 없는 모호함은 질문하세요. 그동안 독립적으로 할 수 있는 작업은 계속하세요.

## 2. 요구사항과 구현 범위

### R1. 회원가입 — 필수

- 가입 입력 항목은 이메일 주소, 이름(닉네임), 비밀번호입니다.
- 회원가입 후 생성한 계정으로 로그인할 수 있어야 합니다.
- 구현 품질 기준: 필수 입력값, 이메일 형식, 이메일 중복, 비밀번호 누락을 검증하고 이해하기 쉬운 오류를 표시하세요. 추가적인 비밀번호 정책을 도입한다면 화면에 안내하세요.
- 원본의 비밀번호 처리는 mock-up이었지만 최신 사용자 지시의 공개 배포·계정 영속성에 맞춰 **비밀번호 해시 기반 인증**으로 변경합니다. 원문 비밀번호를 DB·로그·응답·브라우저 저장소에 보관하지 마세요.
- Werkzeug의 검증된 해시 생성·검증 함수를 사용하고, 데이터베이스에 사용자와 비밀번호 해시를 저장하여 재시작 후에도 동일 계정으로 로그인할 수 있게 하세요.
- **향후:** SNS 로그인으로 대체합니다. 현재 SNS 공급자 연동은 구현하지 마세요.
- **현재:** 비밀번호 전용 단방향 해시 저장을 구현합니다. SNS 로그인으로 교체할 수 있게 인증 코드를 분리하되 불필요한 확장 프레임워크는 만들지 마세요.

### R2. 로그인 — 필수

- 이메일과 비밀번호로 가입한 사용자를 인증할 수 있어야 합니다.
- 로그인 성공·실패를 구분하고, 현재 로그인 사용자와 로그인 상태를 화면 및 권한 판정에 반영하세요.
- 구현 품질 기준: 실패 시 존재하는 이메일 여부를 불필요하게 구분해 노출하지 않는 오류 메시지를 사용하세요.
- 기본 가정: 로그인하지 않은 사용자도 게시글 목록과 상세를 볼 수 있고, 게시글·댓글 작성에는 로그인이 필요합니다. 기존 정책이 있다면 그것을 우선하세요.
- 계정은 앱 재시작 후에도 유지하고 로그인 세션은 최종 계획의 DB 세션·24시간 만료 정책을 따르세요. 재로그인이 필요해져도 저장된 계정·게시글은 유지되어야 합니다.

### R3. 로그아웃 — 필수

- 사용자가 로그아웃할 수 있어야 합니다.
- 로그아웃 즉시 현재 인증 상태를 해제하고 작성·수정·삭제 등 보호된 동작의 권한을 다시 판단하세요.

### R4. 비밀번호 찾기 — 향후

- 현재 비밀번호 재설정, 메일 발송, 토큰 발급은 구현하지 마세요.
- 관련 UI를 제공한다면 “추후 지원”임을 표시하고 실행 가능한 기능으로 오인되지 않게 하세요. UI 자체를 생략해도 됩니다.

### R5. 게시판 — 필수

- 게시글은 **제목과 내용**으로 구성합니다.
- 목록의 게시글 정보는 **제목만** 표시하세요. 내용 요약, 작성자, 작성일, 댓글 수 등 원본에 없는 게시글 메타데이터를 목록에 임의로 추가하지 마세요. 페이지 탐색과 작성 버튼은 별도 UI로 제공할 수 있습니다.
- 목록 항목을 선택하면 제목과 전체 내용을 확인하는 상세 화면으로 이동할 수 있어야 합니다.
- 기본 가정: 자기 글 수정·삭제를 실제로 사용할 수 있도록 로그인 사용자의 게시글 작성 기능을 포함합니다. 작성자 식별자는 로그인 사용자에서 가져오며 닉네임만으로 소유권을 판정하지 마세요.
- 제목·내용이 공백뿐인 글은 저장하지 않도록 검증하세요.

#### R5-1. 페이지 단위 조회 — 필수

- 기본 페이지 크기는 **10개**입니다. 무한 스크롤로 대체하지 마세요.
- 페이지 이동, 현재 페이지, 전체 페이지를 알 수 있게 하고 첫·마지막 페이지의 이동 상태를 올바르게 처리하세요.
- 기본 가정: 최신 글부터 조회하고, 동일한 정렬값에서도 결과가 안정적이도록 고유 식별자를 보조 정렬 기준으로 사용합니다.
- 빈 목록, 마지막 페이지의 일부 항목, 삭제로 현재 페이지가 사라지는 경우를 처리하세요.

#### R5-2. 상세 조회 — 필수

- 목록에서 선택한 글의 제목과 내용을 정확히 표시하세요.
- 존재하지 않거나 삭제된 게시글은 빈 화면이나 예외 대신 적절한 안내를 제공하세요.

#### R5-3. 자기 글 수정·삭제 — 필수

- 로그인 사용자는 **자신이 작성한 게시글만** 수정·삭제할 수 있습니다.
- 다른 사용자의 글에는 수정·삭제 UI를 제공하지 않고, 직접 호출해도 작업을 거부하세요.
- Flask 서버에서 인증 사용자와 저장된 작성자를 비교해 권한을 검증하세요. 클라이언트가 보낸 작성자 ID를 신뢰하지 마세요.
- 수정·삭제 후 목록, 상세, 페이지 상태가 최신 데이터와 일치해야 합니다. 원본에 없는 관리자의 타인 게시글 편집 권한은 임의로 부여하지 마세요.

#### R5-4. 댓글 — 필수

- 게시글별로 댓글을 작성하고 조회할 수 있어야 합니다.
- 기본 가정: 로그인 사용자만 댓글을 작성하고, 공백뿐인 댓글은 거부합니다. 댓글 수정·삭제·대댓글·좋아요는 현재 범위에 추가하지 않습니다.
- 댓글은 대상 게시글과 정확히 연결되어야 하며 다른 게시글의 댓글과 섞이면 안 됩니다.
- 기본 가정: 게시글 삭제 시 해당 글의 댓글도 함께 제거하거나 접근 불가능하도록 일관되게 처리합니다.

#### R5-5. 부적절하거나 불쾌한 표현 마스킹 — 필수

- **키워드 매핑 또는 정규식** 방식으로 표현을 찾아 마스킹하세요. 둘 중 하나를 적절히 선택해도 됩니다. 단순 입력 차단이나 게시글 전체 삭제로 대체하지 마세요.
- 기본 가정: 사용자에게 표시되는 게시글 제목·내용·댓글에 동일한 규칙을 적용합니다. 닉네임 등 다른 필드로 확대하는 것은 별도 요구가 없으면 제외합니다.
- 기본 가정: 일치한 부분을 `***`처럼 일관된 문자열로 대체합니다. 어떤 부분이 치환되는지와 대소문자·공백·단어 경계의 처리 정책을 문서화하세요.
- 공통 마스킹 함수를 사용하고, 중복 키워드나 부분적으로 겹치는 일치가 있어도 결과가 안정적이어야 합니다. 규칙 적용 순서를 정하세요.
- 기본 가정: 원문은 편집 및 규칙 재적용을 위해 데이터 계층에 보존하고, 일반 조회·화면 표시 시 마스킹을 적용합니다. 규칙이 변경되면 기존 글과 댓글에도 반영되도록 하세요. 작성자의 편집 화면에서만 자신의 원문을 사용할 수 있게 하세요.
- 일반 목록·상세·댓글 HTML 응답에 마스킹 전 원문을 숨김 필드·속성·스크립트 등으로 함께 실어 보내지 마세요. 본인 편집 화면에서만 권한 검사 후 원문을 전달하세요.
- 사용자 입력은 안전하게 텍스트로 렌더링하세요. 마스킹은 XSS 방어를 대신하지 않습니다.
- 정규식을 선택했다면 잘못된 패턴을 저장 전에 검증하고, 과도한 처리 시간이나 서비스 중단을 유발할 수 있는 패턴을 제한하세요. 키워드 방식을 선택하면 입력을 임의의 정규식으로 실행하지 마세요.

#### R5-5-1. 초기 규칙 조사와 관리자 관리 — 필수

- **구현 시점에 인터넷 등 최신 자료를 직접 조사**하여 한국어 서비스에 적합한 초기 표현 규칙을 구성하세요. 기억에만 의존하거나 임의의 예시 몇 개를 넣고 최신 조사 완료라고 보고하지 마세요.
- 조사 날짜, 실제 참고한 URL, 초기 규칙 선정 기준, 정상 문장을 잘못 마스킹할 수 있는 한계를 문서화하세요. 맥락 없이 일상 단어·정체성 명칭을 광범위하게 차단하지 않도록 오탐을 검토하세요.
- 네트워크나 도구 제한으로 조사하지 못했다면 그 사실을 밝히고, 임시 예시 규칙과 조사 완료된 규칙을 구분하세요. 이 요구사항은 미완료로 보고하세요.
- 관리자는 마스킹 규칙을 **추가·삭제**할 수 있어야 합니다. 규칙 목록과 추가·삭제 결과를 확인할 수 있는 관리 화면을 제공하세요.
- 사용자 역할을 일반 사용자와 관리자로 구분하고, 관리자는 숨김 비밀번호 입력을 받는 명시적 CLI 명령으로 생성하세요. 공개 회원가입에서 관리자를 선택하거나 스스로 승격할 수 없게 하세요. 배포 DB에 공개된 기본 관리자나 테스트 계정을 넣지 마세요.
- 일반 사용자와 비로그인 사용자는 관리 UI뿐 아니라 규칙 변경 동작에도 접근할 수 없어야 합니다. Flask 서버에서 역할을 검사하세요.
- 빈 규칙과 중복 규칙을 처리하고, 추가·삭제 직후 마스킹 결과에 반영하세요. 규칙 영속성은 선택한 저장 방식과 일치하게 구현하고 재시작 시 유지 여부를 명시하세요.

## 3. 데이터 및 구현 품질 기준

- 최소한 사용자, 게시글, 댓글, 마스킹 규칙을 구분해서 모델링하세요. 사용자 고유 ID와 역할, 게시글 작성자 ID, 댓글의 게시글 ID·작성자 ID처럼 관계와 권한에 필요한 필드를 포함하세요.
- 최종 구성은 Flask 서버·SQLite 영구 저장·PythonAnywhere WSGI 배포입니다. DB 절대 경로를 설정으로 전달하고 소스와 분리하세요. 초기화·시작·배포 업데이트로 기존 데이터를 지우지 말고 백업·복구와 무료 웹앱 만료 관리 절차를 문서화하세요.
- 화면과 데이터 접근·인증·마스킹 로직을 적절히 분리하여 향후 SNS 로그인 및 운영용 인증으로 교체할 수 있게 하되, 사용하지 않는 확장 프레임워크를 만들지 마세요.
- 한국어 UI를 기본으로 하고 입력 라벨, 오류 안내, 키보드 접근성을 갖추세요. 비동기 처리가 있다면 로딩·오류 상태를 제공하고 중복 제출을 방지하세요.
- 테스트용 데이터는 테스트 데이터라고 표시하세요. 운영용 비밀키나 실제 계정 정보를 코드에 넣지 마세요.
