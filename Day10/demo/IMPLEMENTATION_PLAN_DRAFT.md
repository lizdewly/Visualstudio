## 1. 목표와 범위

한국어 게시판 데모를 구성한다. 회원가입 → 로그인 → 게시글 작성·조회 → 자기 글 수정·삭제 → 댓글 작성 → 로그아웃 흐름과 관리자 마스킹 규칙 관리를 구현한다.

| 구분 | 범위 |
| --- | --- |
| 필수 | 이메일·닉네임·비밀번호 회원가입, 로그인, 로그아웃 |
| 필수 | 제목만 보이는 게시글 목록, 페이지당 기본 10개, 상세 조회, 본인 글 수정·삭제 |
| 필수 | 댓글, 키워드 또는 정규식 마스킹, 최신 자료 기반 초기 규칙, 관리자 규칙 추가·삭제 |
| 구현을 위한 기본 가정 | 게시글 작성, 비로그인 조회 허용, 작성 시 로그인 필요, 최신 글 우선 정렬 |
| 향후 | SNS 로그인, 운영용 비밀번호 해시 저장, 비밀번호 찾기 |
| 이번 범위 밖 | 검색, 첨부파일, 좋아요, 대댓글, 댓글 수정·삭제, 사용자 관리, 배포 자동화 |

## 2. 기술 구성 제안

**제안 A: React + TypeScript + Vite 화면, Express + TypeScript API, 서버 메모리 저장소.** 로컬 데모를 기준으로 한다.

| 구성 | 역할 및 선택 이유 |
| --- | --- |
| React + TypeScript | 회원·게시판·관리 화면을 나누고 요청·응답 타입을 명확히 관리 |
| Vite | 프런트엔드 개발 서버와 빌드 구성 |
| Express | 로그인 상태, 글 소유권, 관리자 권한을 서버에서 검사하고 조회 응답에 마스킹 적용 |
| 서버 메모리 저장소 | 계정·콘텐츠·규칙을 같은 수명으로 관리하여 mock 인증과 영속 데이터 간 불일치 방지 |
| 세션 쿠키 | 브라우저에는 임의의 세션 ID만 전달하고 사용자 역할은 서버에서 조회 |
| 일반 CSS | 한국어 폼과 목록 중심의 간결한 반응형 UI 구성 |

프런트엔드와 API는 개발 시 프록시로 연결한다. 요청 시 서버가 세션을 확인하고 서비스 계층에서 권한·검증·마스킹을 수행한 뒤 저장소를 호출한다. 원문과 모의 비밀번호는 일반 조회 응답에 포함하지 않는다.

기술 자료 확인일: 2026-10-27. Vite는 React/TypeScript 프로젝트 템플릿을 제공한다. 런타임은 구현 착수 시 설치된 Node.js와 패키지 요구사항을 확인하고 호환 버전을 고정한다. 참고: [Vite 공식 시작 안내](https://vite.dev/guide/), [Express 5 공식 안내](https://expressjs.com/en/guide/migrating-5/).

**대안 B: 데이터 유지가 필요하면 SQLite 등 로컬 DB를 도입한다.** 다만 mock 계정의 비밀번호를 평문으로 영구 저장하는 구조는 채택하지 않는다. 사용자 ID·계정 재접속·비밀번호 처리 정책까지 함께 다시 결정해야 한다. 피드백 없이 DB 영속화나 운영용 인증으로 범위를 확대하지 않는다.

## 3. 저장 및 인증 정책 제안

| 상황 | 제안 동작 |
| --- | --- |
| 브라우저 새로고침 | 서버 실행 중이면 세션 쿠키로 사용자 상태 복원, 글·댓글·규칙 유지 |
| 로그아웃 | 서버 세션 삭제 및 쿠키 만료, 이후 보호된 API 호출 거부 |
| 서버 재시작 | 사용자·세션·글·댓글·관리자가 변경한 규칙 초기화, 초기 데모 데이터 재생성 |
| 초기 데이터 | 일반 사용자 A·B, 관리자 1명, 페이지 조회용 게시글 21개와 일부 댓글 |
| 가입 역할 | 일반 사용자로 고정, 클라이언트의 역할 지정은 거부 |
| 관리자 권한 | 규칙 관리와 본인 글 편집만 허용, 다른 사용자의 글 편집은 불허 |

모의 비밀번호는 서버 프로세스 메모리에서만 비교하고 로그·파일·응답에 기록하지 않는다. 가입 화면과 문서에 테스트 전용 비밀번호 사용을 표시한다. 관리자 초기 계정은 데모 전용으로 명시한다.

세션은 HttpOnly·SameSite 쿠키를 사용하고 세션 만료 시간을 명시한다. 로컬 HTTP와 향후 HTTPS 환경의 Secure 쿠키 설정을 구분한다. 상태 변경 요청에는 허용된 Origin을 확인하고, 서버는 기본적으로 로컬 인터페이스에 바인딩한다. 이는 로컬 mock 데모이며 운영용 인증 완료를 뜻하지 않는다.

## 4. 화면 및 사용자 흐름

| 화면 경로 제안 | 구성 | 접근 |
| --- | --- | --- |
| `/posts?page=1` | 게시글 제목 목록, 현재/전체 페이지, 이전·다음, 글쓰기 진입 | 누구나 |
| `/signup` | 이메일·닉네임·비밀번호, 검증 안내, 데모 안내 | 비로그인 |
| `/login` | 이메일·비밀번호, 공통 실패 메시지 | 비로그인 |
| `/posts/new` | 제목·내용 입력, 저장·취소 | 로그인 |
| `/posts/:id` | 마스킹된 제목·내용·댓글, 댓글 입력, 본인 글 수정·삭제 | 조회는 누구나, 쓰기는 로그인 |
| `/posts/:id/edit` | 본인 글 원문 편집, 저장·취소 | 작성자만 |
| `/admin/masking` | 키워드 목록, 추가 입력, 삭제 | 관리자만 |

공통 상단에는 서비스명과 로그인 상태에 따른 회원가입·로그인 또는 닉네임·로그아웃을 표시한다. 관리자에게만 규칙 관리 진입점을 표시한다. 목록의 각 게시글에는 제목 외 메타데이터를 표시하지 않는다.

기본 UI는 밝은 배경, 단일 본문 영역, 명확한 입력 라벨과 버튼으로 구성한다. 작은 화면에서도 폼과 페이지 버튼을 사용할 수 있게 한다. 로딩·빈 목록·검증 실패·권한 없음·없는 글 상태를 각각 안내한다.

게시글 생성 후 상세로 이동하고, 수정 후 상세를 다시 조회한다. 삭제 후 원래 목록 페이지로 돌아가되 페이지가 사라졌다면 마지막 유효 페이지로 보정한다. 삭제에는 확인 동작을 둔다. 빈 목록은 첫 페이지에 빈 상태를 표시하고 페이지 이동은 비활성화한다.

## 5. 데이터 모델 제안

| 모델 | 주요 필드 | 관계·규칙 |
| --- | --- | --- |
| User | id, email, nickname, role, createdAt | 정규화한 이메일 중복 불가, role은 USER 또는 ADMIN |
| MockCredential | userId, demoPassword | 서버 메모리 전용, 사용자 응답 모델에서 분리 |
| Session | id, userId, expiresAt | 로그인 시 생성, 로그아웃·만료·재시작 시 제거 |
| Post | id, authorId, titleRaw, contentRaw, createdAt, updatedAt | authorId는 서버 세션에서 결정 |
| Comment | id, postId, authorId, contentRaw, createdAt | 게시글 삭제 시 관련 댓글 함께 삭제 |
| MaskingRule | id, keyword, createdAt | 공백 규칙 거부, 동일 정규화 키워드 중복 거부 |

목록은 createdAt 내림차순, id 보조 정렬을 적용한다. 페이지 크기는 기본 10개로 고정한다. 작성·수정 시 제목·내용·댓글의 공백 여부를 검사하며 길이 상한은 구현 시 상수로 정의해 화면과 서버에서 동일하게 안내한다.

입력 오류·비로그인·권한 없음·없는 리소스·중복을 각각 일관된 상태 코드와 한국어 메시지로 전달한다. UI에서 버튼을 숨기는 것과 별도로 서버에서 모든 쓰기 권한을 검사한다. 생성·수정 응답에도 원문을 불필요하게 반환하지 않는다.

## 7. 마스킹 설계 제안

초기 구현은 **키워드 기반 리터럴 매칭**을 사용한다. 관리자 정규식 입력은 제공하지 않는다.

1. 초기 규칙은 구현 단계에서 최신 공개 자료를 조사하고, 출처 URL·조회일·선정 이유·오탐 사례를 `docs/masking-sources.md`에 기록한다. 현재 조사 완료로 간주하지 않는다.
2. 규칙의 앞뒤 공백을 제거하고 중복을 검사한다. 영문은 대소문자를 구분하지 않으며 특수문자는 문자 그대로 취급한다. 한국어는 부분 문자열 일치를 기본으로 하되 오탐이 많은 짧은 규칙은 초기 목록에서 제외한다.
3. 원문에서 모든 일치 구간을 찾고, 겹치는 구간을 합친 뒤 각 구간을 `***`로 바꾼다. 치환 결과를 다시 검색하지 않아 규칙 순서에 따른 결과 차이를 피한다.
4. 제목·내용·댓글은 동일 함수로 처리한다. 닉네임은 현재 범위에서 제외한다.
5. 원문은 서버에 보존하고 조회마다 현재 규칙을 적용한다. 사용자에게 전달하는 일반 응답에는 원문을 포함하지 않는다. 작성자 편집 API만 소유권 검사 후 원문을 제공한다.
6. 규칙 변경은 저장 성공 직후 이후 조회에 반영한다. 이미 열린 다른 브라우저 화면은 다음 조회·새로고침 때 반영하며 실시간 푸시는 범위에 포함하지 않는다.
7. 정상 문장·반복 일치·겹친 일치·특수문자·규칙 추가 및 삭제를 검증한다. 공백 삽입 등 모든 우회 표현을 탐지한다고 주장하지 않는다.

| R2~R3 | 로그인 성공·실패·로그아웃, 세션 무효화 후 보호된 API 거부 |
| R4 | 비밀번호 찾기는 향후 기능으로 문서화, 활성 기능으로 노출하지 않음 |
| R5 | 제목·내용 작성, 공백 저장 거부, 목록에는 제목만 표시 |
| R5-1 | 0·1·10·11·21개 데이터, 최신순·페이지별 항목 수, 마지막 항목 삭제 후 페이지 보정 |
| R5-2 | 올바른 상세 조회, 없는 글·삭제된 글 안내 |
| R5-3 | A는 A의 글만 수정·삭제, B·비로그인·관리자의 타인 글 변경 거부, 위조 authorId 무시 또는 거부 |
| R5-4 | 댓글 생성·조회, 글 간 분리, 공백·비로그인 작성 거부, 게시글 삭제 시 댓글 정리 |
| R5-5 | 모든 대상 필드 마스킹, 정상 문장 유지, 반복·겹침·특수문자 처리, 일반 응답 원문 비노출 |
| R5-5-1 | 조사 출처·날짜, 관리자 추가·삭제, 일반 사용자 직접 호출 차단, 기존 글에 변경 규칙 반영 |
| 공통 | 새로고침 시 유지 및 재시작 시 초기화 정책, 사용자 입력의 텍스트 렌더링, 키보드 및 작은 화면 사용 |

마스킹 함수는 단위 테스트, 인증·권한·페이지 조회는 API 통합 테스트로 검증한다. 가입부터 댓글·편집·로그아웃까지 사용자 흐름과 관리자 규칙 변경은 브라우저에서 점검한다. 구체적인 테스트 도구는 최종 스택에 맞춰 선택한다.

최종 구현 보고에는 실제 수행한 명령과 결과를 기록한다. 아직 실행하지 않은 검사, 초기 규칙 조사 실패, 미완료 기능을 통과 또는 완료로 표시하지 않는다.

## 11. 사용자 피드백 요청 및 최종화 방법

다음 두 항목을 우선 확인한다. 나머지 화면·권한·마스킹 정책도 원하는 변경 사항이 있으면 함께 반영한다.

| 결정 항목 | 현재 제안 | 변경 가능 예 |
| --- | --- | --- |
| 기술 스택 | React + TypeScript + Vite / Express | 학습·업무에서 사용하는 별도 언어 또는 프레임워크 |
| 데이터 수명 | 서버 재시작 시 전체 초기화하는 로컬 데모 | 재시작 후에도 계정·게시글·댓글·규칙 유지 |

사용자 피드백을 받은 뒤 아래 순서로 최종화한다.

1. 피드백과 기준 요구사항의 충돌 여부를 확인하고, 사용자가 명시적으로 바꾼 범위를 기록한다.
2. 기술 선택만 바꾸지 않고 관련 화면·API·인증·저장·테스트 계획까지 함께 수정한다.
3. 해결되지 않은 결정이 있다면 해당 항목만 추가 확인한다. 답변이 없는 상태를 승인으로 간주하지 않는다.
4. 초안은 보존하고 최종본을 `IMPLEMENTATION_PLAN.md`에 저장한다. 확정된 선택과 변경 이력을 포함한다.
5. 이번 요청의 완료 범위는 최종 계획 문서 저장이다. 애플리케이션 구현은 후속 요청에 따라 시작한다.
