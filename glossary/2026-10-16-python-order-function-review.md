## 질문

`Day_3/day3-7` 코드에 함수가 하나 있다. 문제점이 없는지 정밀 분석해 달라.

## 답변

분석 대상은 `calc_order_legacy(u_type, price, qty, coupon)`이다. 원본 코드는 수정하지 않고 실행 결과를 확인했다.

### 1. 확정 오류: 등급 분기의 변수명 오타

7행의 `elif u_tyoe == 3:`에서 `u_tyoe`는 정의되지 않았다. 매개변수 이름인 `u_type`으로 고쳐야 한다.

`u_type`이 1 또는 2이면 앞의 조건이 성립하므로 이 줄을 평가하지 않는다. 따라서 현재 예제만 실행하면 오류가 숨겨진다. 3이나 0처럼 앞의 두 조건에 맞지 않는 값에서는 `NameError`가 발생한다. 문법 검사로는 이 오류를 발견하지 못한다. 변수 이름 자체는 문법상 유효하기 때문이다.

### 2. 호출 예제와 쿠폰 조건의 대소문자 불일치

9행은 `coupon == "YES"`만 인정하지만, 15행의 호출은 `"yes"`를 전달한다. 문자열 비교는 대소문자를 구별하므로 쿠폰 할인이 적용되지 않는다.

현재 결과는 `100 × 20 × 0.95 = 1900`이다. 같은 호출에 `"YES"`를 전달하면 `1900 - 3000`이 음수여서 0을 반환한다. 대문자만 받는 계약이라면 예제 호출을 바꾸면 된다. 소문자와 앞뒤 공백도 허용하려면 문자열인지 확인한 후 `coupon.strip().upper()`로 비교할 수 있다. `None`에 바로 문자열 메서드를 호출하면 다른 오류가 발생하므로 입력 규칙도 정해야 한다.

### 3. 입력 검증 부재

현재 외부 입력을 직접 받는 코드는 없으므로 아래 항목은 함수 재사용 시의 위험이다. 허용하는 입력을 정한 다음 검증을 추가하는 것이 좋다.

- 등급: 오타를 고친 후에도 1·2·3 이외의 값은 조용히 등급 할인 없이 계산된다. 일반 등급을 허용할지, 잘못된 값으로 거부할지 결정해야 한다.
- 가격·수량: 음수를 검사하지 않는다. 둘 다 음수이면 양수 주문 금액이 되고, 한쪽만 음수이면 마지막에 0으로 바뀌어 잘못된 입력이 감춰진다. 최종 금액의 음수 보정은 입력 검증을 대신하지 않는다.
- 수량: `1.5` 같은 소수도 계산된다. 낱개 상품이라면 정수 제한이 필요하지만, 무게로 판매한다면 소수 수량이 유효할 수 있다.
- 타입: 문자열 가격은 연산 중 `TypeError`를 일으킬 수 있다. `True == 1`이므로 `True`도 1등급으로 처리된다. 정수 타입을 검사할 때도 불리언 허용 여부를 고려해야 한다.
- 쿠폰: `None`이나 오타 문자열도 오류 없이 쿠폰 미사용으로 취급된다. 이를 허용할지 정해야 한다.

### 4. 소수점 및 금액 계산 규칙

`return int(total)`은 반올림하지 않고 소수 부분을 버린다. 이 함수에서는 음수를 먼저 0으로 보정하므로 결과적으로 양수 금액의 소수 부분이 버려진다. 예를 들어 가격 101, 수량 1, 1등급, 쿠폰 미사용이면 95를 반환한다. 반올림이 필요한지는 별도 요구사항이다.

`0.95`, `0.90`은 부동소수점 값이다. 작은 예제에서 항상 잘못된 정수가 나온다는 뜻은 아니지만 정확한 금액 계산에는 한계가 있다. 매우 큰 정수 금액에서는 정수 기반 내림 계산과 1 차이가 나는 사례를 실제 확인했다.

가격과 수량이 정수이고 정책이 원 단위 내림이면 `price * qty * 95 // 100` 같은 정수 연산을 고려할 수 있다. 반올림이나 소수 가격을 지원하려면 그에 맞는 규칙을 먼저 정해야 한다. `Decimal`은 파이썬 표준 라이브러리의 다른 선택지다.

### 5. 확인해야 할 계산 정책

현재 순서는 등급 할인 → 쿠폰 3000 차감 → 음수면 0 → 정수 변환이다. 이 순서 자체는 오류가 아니다. 할인 순서, 중복 할인 가능 여부, 최소 주문 금액, 반올림 기준에 대한 요구사항이 있어야 옳고 그름을 판정할 수 있다.

함수는 금액을 반환하는 역할만 수행하며, 출력은 함수 밖에서 한다. 이 분리는 적절하다. `print (result)`의 공백이나 매개변수 이름의 축약은 실행 오류의 원인이 아니다. 파일에 `.py` 확장자가 없어도 `python Day_3/day3-7`로 실행할 수 있다.

## 헷갈리기 쉬운 점

- 문법 검사 통과는 모든 입력에 대한 정상 동작을 보장하지 않는다. `if`와 `elif`의 각 경로를 실행해야 오타처럼 숨어 있는 오류가 드러난다.
- 대문자만 쿠폰으로 인정하는 것이 의도라면 비교식은 유효하다. 다만 현재 호출의 소문자와 일치하지 않는다.
- 잘못된 입력과 정상 주문에 쿠폰을 적용해 0이 되는 경우는 구분해야 한다.
- 큰 금액에서 확인한 부동소수점 차이를 모든 작은 주문에서도 발생하는 오류로 일반화하면 안 된다.

## 후속 질문과 답변

### 2026-10-16: 재사용과 유지보수 측면의 개선점

질문: 재사용과 유지보수 측면의 개선점은 없어?

답변: 있다. 앞선 분석은 실행 오류와 계산 정확성 중심이었다. 다른 파일에서 가져다 쓰거나 할인 정책을 바꾸는 상황에서는 다음 개선이 유용하다. 아래는 설계 제안이며 원본 파일에는 적용하지 않았다.

| 개선점 | 현재 불편한 점 | 개선 방향 |
| --- | --- | --- |
| 의미가 분명한 이름 | `u_type`, `qty`, `legacy`만으로 역할을 파악하기 어렵다 | `member_grade`, `quantity`, `calculate_order_total`처럼 목적을 드러낸다. `price`는 개당 가격이면 `unit_price`로 표현한다. |
| 할인 정책을 한곳에 모으기 | 등급별 계수와 쿠폰 금액이 계산문에 직접 들어 있다 | 등급별 할인율 딕셔너리와 `COUPON_DISCOUNT` 같은 상수로 관리한다. |
| 문자열 입력과 계산 분리 | 계산 함수 사용자가 `"YES"`라는 표기 규칙까지 알아야 한다 | 호출부에서 문자열을 해석하고 함수에는 `has_coupon=True` 같은 불리언을 전달한다. 잘못된 문자열의 처리 규칙도 정한다. |
| 입력·반환 규칙 문서화 | 가격 단위, 수량 타입, 미지원 등급, 반올림 정책을 호출자가 추측해야 한다 | 함수 첫 부분의 설명 문자열(docstring)에 허용 입력, 할인 순서, 반환값과 예외를 적고 필요한 검증을 구현한다. |
| 가져오기와 예제 실행 분리 | 다른 모듈에서 함수를 가져와도 파일 마지막의 출력이 실행된다 | 예제 호출을 `if __name__ == "__main__":` 아래로 옮긴다. 일반적인 import를 위해 `day3_7.py` 같은 파일명을 사용한다. |
| 정책 변경 후 결과 확인 | 현재 예제 하나는 1등급만 확인하고 오타를 놓친다 | 1·2·3등급, 쿠폰 유무, 최종 금액 0, 잘못된 입력, 소수 금액 처리 사례를 확인한다. |

할인 규칙을 모으는 형태의 예시:

```python
DISCOUNT_PERCENT = {1: 5, 2: 10, 3: 20}
COUPON_DISCOUNT = 3000
```

여기서 `5`는 할인율 5%다. 기존 코드의 `0.95`는 할인 후 지불 비율 95%이므로 혼동하지 않아야 한다. 딕셔너리는 정책을 한곳에서 읽고 바꾸게 해 주지만, 그 자체로 모든 할인 정책에 유연해지는 것은 아니다. 미지원 등급에 기본값을 줄지 오류를 낼지는 별도로 정해야 한다.

호출 의도를 드러내는 예시 형태:

```python
calculate_order_total(
    member_grade=1,
    unit_price=100,
    quantity=20,
    has_coupon=True,
)
```

이는 개선 후 인터페이스를 보여 주는 예시이며 현재 함수로 실행할 수 있는 코드는 아니다. 매개변수 이름이나 쿠폰 타입을 바꾸면 기존 호출부도 함께 수정해야 한다. `bool("NO")`는 `True`이므로 문자열을 단순히 `bool()`로 바꾸면 안 된다. 타입 힌트를 추가해도 런타임에 잘못된 입력을 자동 차단하지는 않는다.

직접 실행용 예제를 분리하는 형태:

```python
if __name__ == "__main__":
    result = calc_order_legacy(1, 100, 20, "YES")
    print(result)
```

이 구조는 import할 때 예제 호출과 출력을 건너뛰게 한다. 기존 함수의 변수명 오타 등은 별도로 수정해야 한다. 현재 `day3-7`은 확장자가 없고 이름에 하이픈이 있어 일반적인 `import day3_7`에 사용할 이름과 맞지 않는다. `day3_7.py`로 정리하면 다른 파일에서 재사용하기 편해진다.

현재처럼 짧은 학습 코드에서는 함수가 금액을 반환하고 출력은 밖에서 하는 구조를 유지하면 충분하다. 등급 할인 한 줄, 쿠폰 차감 한 줄을 모두 별도 함수나 클래스로 나눌 필요는 없다. 같은 계산이 여러 곳에 반복되거나 특정 규칙이 복잡해질 때 추가 분리를 고려한다. 함수는 이미 전역 상태를 변경하지 않아 같은 입력의 결과를 비교하기 쉬운 구조다.
