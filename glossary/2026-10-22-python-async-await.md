## 답변

비동기는 기다리는 시간을 다른 작업에 활용할 수 있도록 코드를 구성하는 방식이다. 카페에서 커피가 내려오는 동안 차를 준비하는 상황에 비유할 수 있다.

| 표현 | 역할 |
| --- | --- |
| `async def` | 중간에 기다리며 실행을 양보할 수 있는 코루틴 함수를 정의 |
| `await 작업` | 그 작업의 완료와 결과를 기다림. 기다리는 동안 실행을 양보하면 다른 예약된 작업이 진행 가능 |
| `asyncio.run(main())` | 일반 Python 스크립트에서 이벤트 루프를 만들어 비동기 실행을 시작하고 종료까지 관리 |
| `await asyncio.gather(a(), b())` | 두 코루틴을 함께 진행하도록 예약하고 모두 완료될 때까지 기다림 |

코루틴 함수는 호출만 하면 코루틴 객체가 만들어진다. 함수 본문을 실행하려면 await하거나 asyncio로 실행을 관리해야 한다. 이벤트 루프는 실행 가능한 작업을 골라 진행시키는 담당자다.

`await` 뒤의 코드가 곧바로 실행되는 것은 아니다. 현재 코루틴은 기다리는 작업이 완료된 후 다음 줄로 넘어간다. 그 사이에 진행할 수 있는 것은 다른 예약된 작업이다. 또한 await 대상이 이미 완료됐거나 중단 없이 끝나면 반드시 다른 작업에 실행권을 넘기는 것은 아니다.

## 예제

현재 파일의 함수는 2초의 대기 시간을 음료 제조에 비유한다.

```python
import asyncio

async def make_drink(name):
    print(f'{name} 만들기 시작')
    await asyncio.sleep(2)
    print(f'{name} 완성')
    return name
```

`asyncio.sleep(2)`를 await하는 동안 이 코루틴은 멈추고, 이벤트 루프는 다른 작업을 진행할 수 있다. 완료 후 `return name`의 값을 받을 수도 있다.

```python
result = await make_drink('커피')  # async 함수 안에서 사용
```

현재 `main()`의 두 await는 순차 실행이다.

```python
async def main():
    await make_drink('커피')
    await make_drink('차')

if __name__ == '__main__':
    asyncio.run(main())
```

커피를 기다려 완료한 다음 차를 시작하므로 약 4초가 걸린다. 현재 원본 파일의 마지막 줄은 `main()`이다. 비동기 함수를 이렇게 호출만 하면 본문이 실행되지 않으므로, 스크립트를 실행하려면 위처럼 `asyncio.run(main())`을 사용해야 한다. 실행하지 않은 코루틴에 대한 RuntimeWarning이 나올 수 있다. 이 설명 작업에서는 원본 파일을 변경하지 않았다.

두 음료를 함께 진행하려면 다음처럼 `main()`을 작성한다.

```python
async def main():
    results = await asyncio.gather(
        make_drink('커피'),
        make_drink('차'),
    )
    print(results)

if __name__ == '__main__':
    asyncio.run(main())
```

두 작업의 2초 대기가 겹치므로 약 2초가 걸린다. 모두 정상 완료되면 반환값은 전달한 순서대로 리스트에 담겨 `['커피', '차']`가 된다. 각 작업이 더 빨라진 것이 아니라 대기 시간이 겹친 것이다.

```text
순차: 커피 [2초 대기] 완료 → 차 [2초 대기] 완료
함께: 커피 [2초 대기] 완료
      차   [2초 대기] 완료
```

## 실행 확인

원본의 `make_drink`를 import해 임시 명령에서 순차 실행과 `asyncio.gather` 실행을 각각 확인했다. 원본 파일을 직접 실행하거나 변경한 것이 아니다.

- 순차 실행: 4.01초
- 함께 진행: 2.00초
- 두 실행 모두 정상 종료했다. 측정값은 환경마다 조금 달라질 수 있다.
- 도구 출력의 한국어 인코딩이 깨져 보여 전체 출력문은 그대로 옮기지 않았다.

## 헷갈리기 쉬운 점

- `async def`만 붙인다고 여러 작업이 자동으로 함께 실행되지는 않는다.
- 일반 `.py` 파일에서 `await`는 `async def` 내부에 쓴다. 일부 대화형 환경의 최상위 await와 구분한다.
- `await`에는 코루틴·태스크 같은 기다릴 수 있는 객체가 필요하다. 일반 함수 호출에 무조건 붙이는 문법이 아니다.
- `time.sleep(2)`는 현재 스레드를 막는다. 이벤트 루프 스레드 안에서 실행하면 그 루프의 다른 작업도 진행하지 못한다. `await asyncio.sleep(2)`는 다른 작업이 진행할 기회를 준다.
- 웹 요청이나 비동기 DB 조회처럼 대기가 많은 작업에 유용하다. 복잡한 계산 자체를 자동으로 빠르게 만들거나 CPU 여러 개에서 병렬 실행하는 문법은 아니다.
- 이미 이벤트 루프가 실행 중인 환경에서는 같은 스레드에서 `asyncio.run()`을 중첩 호출하지 않는다. 비동기 함수 안에서는 보통 `await`로 연결한다.

### 2026-10-22: Day_7/02의 동기·비동기 차이와 async/await 제거

질문: `Day_7/02` 폴더 내용으로 동기와 비동기의 차이를 설명하고, async/await 없이 실행하면 어떤 차이가 있는지 알려 달라.

확인한 파일:

- `01.fetch.py`: `asyncio.run(main(1))`으로 비동기 함수를 실행해 외부 `/posts/1`에 요청 한 번을 보내고 응답과 제목을 출력한다. 변수 이름은 todo_id지만 실제 요청 경로는 posts다.
- `main.py`: FastAPI의 `/todos/{todo_id}`가 외부 `/todos/{todo_id}` 데이터를 조회한 뒤 id, title, completed를 응답한다. 비동기 경로 함수는 FastAPI가 실행하므로 여기에는 asyncio.run을 추가하지 않는다.

흐름은 사용자 → FastAPI의 read_todo → fetch_todo → 외부 서버 → 결과를 사용자에게 반환하는 순서다.

`await client.get(...)`는 외부 응답을 기다리는 동안 현재 코루틴의 진행을 멈추고 이벤트 루프가 다른 작업을 진행할 수 있게 한다. 같은 함수의 다음 줄은 응답이 온 뒤 실행된다. `await fetch_todo(...)`도 결과가 나온 뒤에야 data에 값을 넣는다. await는 결과를 기다리지 않고 다음 줄로 넘어간다는 뜻이 아니다.

동기 HTTP 호출은 응답이 올 때까지 현재 스레드를 막는다. 비동기 HTTP 호출은 기다리는 동안 같은 이벤트 루프가 다른 요청 등을 처리할 수 있게 한다. 요청 하나 자체가 더 빨라지는 것은 아니다. `01.fetch.py`는 현재 요청 한 개뿐이라 비동기의 동시 처리 효과를 크게 체감하기 어렵다. main.py에서는 여러 사용자 요청이 들어왔을 때 대기를 겹칠 수 있다. 한 함수에서 외부 요청 여러 개를 함께 진행하려면 gather 등으로 별도 구성해야 한다.

| 코드 | 역할 |
| --- | --- |
| `async def` | 비동기 함수를 정의. 호출하면 코루틴 객체가 생성됨 |
| `httpx.AsyncClient` | 비동기 HTTP 클라이언트 |
| `async with` | 비동기 클라이언트의 사용 범위를 정하고 종료 시 정리 |
| `await client.get(...)` | 요청을 실행하고 응답을 기다림 |
| `response.json()` | 이미 받은 JSON 응답을 파이썬 값으로 변환. 이 예제에서 await는 불필요 |
| `asyncio.run(main(1))` | 독립 스크립트에서 이벤트 루프를 관리하며 main 실행 |

단순히 키워드를 삭제하는 것과 올바른 동기 코드로 바꾸는 것은 다르다.

- `response = client.get(...)`처럼 AsyncClient 호출에서 await만 지우면 response는 HTTP 응답이 아니라 코루틴 객체다. 이어서 response.status_code 또는 response.json()을 사용하면 오류가 발생한다. 그 호출만으로 HTTP 요청을 완료하지 않는다.
- `data = fetch_todo(todo_id)`에서 await만 지우면 data도 코루틴이며 `data.get(...)`을 사용할 수 없다.
- `async def`를 `def`로 바꾸고 await나 async with를 남기면 문법 오류가 난다.
- AsyncClient를 그대로 두고 async with를 일반 with로 바꾸는 것도 올바른 동기 변환이 아니다.
- 스크립트 main을 일반 def로 바꿨다면 `asyncio.run(main(1))` 대신 `main(1)`로 호출한다.

올바른 동기 방식의 설명용 예제(원본 파일은 변경하지 않았으며 아래 코드는 실행하지 않음):

```python
def fetch_todo(todo_id):
    with httpx.Client(base_url=Base_URL, timeout=10.0) as client:
        response = client.get(f"/todos/{todo_id}")
        response.raise_for_status()
        return response.json()

@app.get("/todos/{todo_id}")
def read_todo(todo_id: int):
    data = fetch_todo(todo_id)
    return {
        "id": data.get("id", todo_id),
        "title": data.get("title", "제목 없음"),
        "completed": data.get("completed", False),
    }
```

FastAPI는 일반 def 경로 함수를 스레드풀에서 실행한다. 따라서 위 동기 예제가 서버 전체를 반드시 정지시키는 것은 아니다. 반대로 async def 경로를 유지한 채 안에서 동기 httpx.Client 호출을 직접 하면 이벤트 루프를 막는다. FastAPI가 직접 실행하는 경로 함수와, 우리가 직접 호출하는 일반 보조 함수를 구분해야 한다. 보조 함수 호출이 자동으로 스레드풀에 옮겨지는 것은 아니다.

현재 원본 main.py의 별도 주의점: `response.raise_for_status()`가 없으므로 HTTP 오류 상태만으로 `httpx.HTTPStatusError`가 발생하지 않는다. 이 호출을 추가해 오류를 잡더라도 현재 except에서 출력만 하고 계속 진행하면 data가 할당되지 않아 오류가 날 수 있으므로 HTTPException을 발생시키거나 적절한 응답을 반환해야 한다. 이번 요청은 설명이므로 소스 수정이나 외부 API 실행은 하지 않았다.

### 2026-10-22: 동기 방식으로도 구현 가능한가? 버그나 오류 요소는?

가능하다. Day_7/02처럼 외부 API를 조회해 반환하는 기능은 `def` 경로 함수와 `httpx.Client`로 구현할 수 있다. 동기라는 이유 자체로 오류가 발생하지는 않는다. FastAPI는 일반 def 경로 함수를 스레드풀에서 실행한다. 다만 많은 느린 요청이 몰리면 사용 가능한 스레드가 부족해 추가 요청이 대기할 수 있다. 이는 문법 오류가 아닌 처리량과 지연 문제다.

주의할 요소:

1. async def 경로에서 동기 Client 호출을 직접 실행하면 이벤트 루프를 막는다. 경로 함수까지 def로 바꾸거나 별도로 스레드에 작업을 넘겨야 한다.
2. 동기 Client의 get 결과에 await를 붙이거나, AsyncClient에 await 없이 일반 응답처럼 접근하면 오류가 난다. Client/with/def 조합을 맞춘다.
3. `timeout=10.0`이어도 서버 지연 등으로 httpx.TimeoutException이 발생할 수 있다. 이 설정은 단순한 전체 요청 10초 제한과 같지는 않다.
4. DNS, 연결 거부, 네트워크 단절 등은 httpx.RequestError로 처리할 수 있다. TimeoutException은 RequestError의 하위이므로 먼저 처리한다.
5. HTTP 오류 상태는 response.raise_for_status()로 검사한다. 현재 원본은 이 호출이 없어 HTTPStatusError 처리 코드가 기대대로 동작하지 않을 수 있다.
6. 예외를 출력만 하고 계속 진행하면 data가 할당되지 않은 채 참조될 수 있다. 예외 처리에서 HTTPException을 발생시키거나 응답을 반환해야 한다.
7. 응답이 JSON이 아니면 JSON 변환 오류가 나며, JSON이라도 리스트/null이면 data.get을 사용할 수 없다. dict인지 확인하고 필요하면 필드 타입도 검증한다.
8. with httpx.Client(...)를 사용하면 정상 종료와 예외 발생 시 클라이언트를 정리한다. 각 요청마다 새 Client를 만드는 구조는 학습용으로 간단하지만 연결 재사용 효율은 떨어질 수 있다.

동기·비동기 모두 네트워크 오류, HTTP 상태 오류, 잘못된 응답 형식을 처리해야 한다. HTTP 404를 정상 데이터처럼 기본값으로 채워 성공 응답으로 돌려주는 것도 현재 코드에서 가능한 논리 오류다. 이번 답변에서는 원본 소스를 수정하거나 실행하지 않았다.

### 2026-10-22: 스레드·스레드풀과 동시 처리, 비동기의 대기 겹치기

질문: 스레드/스레드풀에서 처리한다는 의미와, 동기 호출도 스레드로 여러 작업을 동시에 처리할 수 있다는 말 및 비동기 호출은 대기를 겹친다는 말을 더 자세히 설명해 달라.

스레드는 한 프로그램 안에서 코드를 실행하는 흐름이다. 프로세스가 가게라면 스레드는 직원에 비유할 수 있다. 스레드풀은 작업에 배정할 스레드를 제한된 수로 관리하고 재사용하는 장치다. 모든 스레드가 바쁘면 새 작업은 여유가 생길 때까지 기다린다. 구현에 따라 스레드는 필요할 때 생성하므로, 항상 전부 미리 만들어 둔다는 뜻은 아니다.

FastAPI가 일반 def 경로 함수를 스레드풀에서 처리한다는 것은 요청 처리를 작업 스레드에 맡기고, 이벤트 루프는 다른 작업을 계속할 수 있다는 뜻이다. 해당 작업 스레드는 동기 HTTP 호출의 응답을 기다리는 동안 막히지만 다른 스레드까지 함께 멈추지는 않는다. 일반 def 함수 내부의 세 호출이 자동으로 세 스레드에 분배되는 것은 아니다. 순서대로 호출하면 한 요청 안에서는 그대로 순차 실행된다.

각 요청이 외부 응답을 2초 기다리고 서로 독립적이며 자원 제한이 없다고 가정하면:

| 구성 | 기다리는 방식 | 세 작업의 예상 전체 시간 |
| --- | --- | --- |
| 스레드 1개에서 동기 호출 세 번 | A 완료 후 B, B 완료 후 C | 약 6초 |
| 작업 스레드 3개에 동기 호출 배정 | 각 스레드가 자기 작업의 응답을 기다림 | 약 2초 |
| 이벤트 루프에서 비동기 작업 세 개 예약 | A가 대기하면 B, B가 대기하면 C를 진행 | 약 2초 |

동기 스레드 방식도 외부 I/O 대기 시간을 겹칠 수 있다. 두 방식의 차이는 시간을 겹칠 수 있느냐가 아니라 대기 중인 작업을 어떤 실행 구조로 관리하느냐다. 동기는 기다리는 작업마다 스레드를 점유하고, 비동기는 I/O 대기 시 실행을 양보하여 적은 스레드로 많은 작업을 관리할 수 있다. 위 시간은 설명용 가정이며 실측이 아니다.

```text
동기 순차: A [대기 2초] → B [대기 2초] → C [대기 2초]
스레드 3개: 스레드1 A [대기 2초]
             스레드2 B [대기 2초]
             스레드3 C [대기 2초]
비동기: 한 이벤트 루프가 A/B/C를 시작하고,
        각 I/O 대기 중에는 다른 작업으로 전환하며 완료된 작업을 재개
```

비동기는 한 스레드에서 같은 순간에 파이썬 코드 세 줄을 실행한다는 뜻이 아니다. 기다리는 동안 다른 작업을 진행하는 동시성이다. 여러 CPU에서 계산을 실제로 동시에 실행하는 병렬성과 구별한다. 기본적인 CPython 환경에서는 GIL 때문에 파이썬 계산 작업에 스레드를 추가한다고 CPU 성능이 비례해서 늘지는 않는다. 네트워크처럼 I/O 대기가 많은 상황과 무거운 계산을 구별해야 한다.

```python
# 비동기 함수라도 이렇게 쓰면 세 요청은 순차 실행
a = await fetch_todo(1)
b = await fetch_todo(2)
c = await fetch_todo(3)

# 함께 진행하도록 예약해야 대기를 겹칠 수 있음
a, b, c = await asyncio.gather(
    fetch_todo(1), fetch_todo(2), fetch_todo(3)
)
```

위 코드는 async 함수 내부에 넣는 설명용 예제다. HTTPX AsyncClient를 사용하는 기존 비동기 fetch_todo를 전제로 하며 이번 답변에서 실행하지 않았다. 동기 함수를 스레드로 배정하는 도구로는 표준 라이브러리의 ThreadPoolExecutor가 있다.

카페 비유에서 동기 스레드 방식은 직원 여러 명이 각각 자기 주문을 기다리는 방식이고, 비동기는 직원이 한 주문의 기계 작업 완료를 기다리는 동안 다른 주문을 진행하는 방식이다. 실제 OS와 네트워크 구현을 단순화한 비유다.

### 2026-10-22: 코루틴이란?

질문: 코르틴은 뭐야?

보통 코루틴(coroutine)이라고 부른다. 실행 중 잠시 멈췄다가 나중에 이어서 실행할 수 있는 작업이라고 이해하면 된다. 파이썬에서는 async def로 코루틴 함수를 정의하며, 그 함수를 호출하면 코루틴 객체가 만들어진다. 코루틴 객체는 함수 실행을 진행하고 일시 중단·재개할 수 있게 하는 객체이며, 함수 호출만으로 본문이 실행되지는 않는다.

```python
import asyncio

async def fetch():
    print("요청 시작")
    await asyncio.sleep(2)
    print("응답 도착")
    return "데이터"

async def main():
    job = fetch()        # 코루틴 객체 생성: fetch 본문은 아직 실행 안 됨
    result = await job  # 실행을 진행하고 완료 결과를 받음
    print(result)

asyncio.run(main())
```

위 코드는 설명용이며 이번 답변에서 실행하지 않았다. 코드상 예상 순서는 요청 시작 출력 → 약 2초 대기 → 응답 도착 출력 → 데이터 출력이다. sleep을 기다리는 동안 다른 예약된 작업이 있으면 이벤트 루프가 그 작업을 진행할 수 있다. 이 예제 자체에는 동시에 수행할 별도 작업이 없다. await마다 반드시 실제 일시 중단이 발생하는 것은 아니다.

| 표현 | 의미 |
| --- | --- |
| `fetch` | 코루틴 함수 자체 |
| `fetch()` | 코루틴 객체 생성 |
| `await fetch()` | 실행을 진행하고 결과를 기다림 |
| `asyncio.create_task(fetch())` | 코루틴을 태스크로 감싸 이벤트 루프에 실행 예약 |
| `asyncio.run(main())` | 독립 스크립트에서 이벤트 루프를 관리하며 main 실행 |

스레드는 코드를 실행하는 흐름이고, 코루틴은 그 위에서 진행되는 일시 중단·재개 가능한 작업이다. 코루틴 하나가 스레드 하나를 새로 만드는 것은 아니다. 이벤트 루프 하나가 여러 코루틴을 번갈아 진행할 수 있다. coroutine이라는 이유만으로 자동 동시 실행되거나 별도 CPU에서 병렬 실행되는 것은 아니다.

Day_7/02/main.py의 `data = await fetch_todo(todo_id)`에서는 코루틴 함수 fetch_todo를 호출해 코루틴 객체를 만들고, await로 실행 및 완료를 기다려 반환된 데이터를 data에 넣는다. await 없이 `data = fetch_todo(todo_id)`만 쓰면 data는 조회 결과가 아니라 코루틴 객체다. await 또는 태스크 예약 등 없이 버려진 코루틴에는 실행되지 않았다는 RuntimeWarning이 나올 수 있다.

### 2026-10-22: FastAPI GET·PUT·DELETE 등의 경로에서 동기·비동기를 선택하는 기준

질문: FastAPI로 외부 입력을 처리하는 GET, PUT, DELETE 등의 서비스를 구성할 때 언제 동기/비동기 경로를 설정하는지 대표적인 경우를 간단한 표로 정리해 달라.

HTTP 메서드가 아니라 경로 안에서 사용하는 작업과 라이브러리의 방식에 따라 선택한다. FastAPI는 웹 프레임워크이고 실제 네트워크 요청 수신은 Uvicorn 같은 서버가 맡는다.

| 대표 작업 | 경로 함수 선택 | 이유·예 |
| --- | --- | --- |
| 간단한 JSON 반환, 가벼운 입력 검사 | 둘 다 가능, async def도 적합 | 오래 기다리거나 계산하지 않는 작업 |
| 동기 DB 라이브러리로 조회·수정·삭제 | def | 동기 DB 호출이 현재 스레드를 막으므로 스레드풀에서 처리 |
| 비동기 DB 라이브러리로 조회·수정·삭제 | async def + await | DB 응답 대기 중 다른 작업 진행 가능 |
| requests 또는 httpx.Client로 외부 API 호출 | def | 동기 HTTP 호출 |
| httpx.AsyncClient로 외부 API 호출 | async def + await | 비동기 HTTP 호출 |
| 일반 파일 읽기·쓰기, 느린 동기 라이브러리 | def 또는 별도 스레드로 분리 | async 경로에서 직접 실행하면 이벤트 루프를 막을 수 있음 |
| 독립적인 외부 API 여러 개 동시 조회 | async def + await asyncio.gather(...) | 비동기 호출들의 대기 시간 겹치기 |
| 영상 변환·무거운 계산 | 별도 프로세스/작업 큐로 분리 | async를 붙여도 계산이 빨라지지 않음 |

일반 def 경로는 FastAPI가 스레드풀에서 실행한다. async def 안에서 직접 호출한 일반 보조 함수가 자동으로 스레드풀로 옮겨지는 것은 아니다. GET뿐 아니라 POST·PUT·DELETE에도 같은 기준이 적용된다. 이번 답변에서는 소스 코드를 수정하거나 실행하지 않았다.

### 2026-10-22: 경로 함수의 def/async def를 고르는 실제 규칙

질문: 어떤 규칙과 기준으로 route를 설정하라는 것인가?

앞선 대화 맥락에서 route의 def/async def 선택을 뜻한다. URL 경로와 HTTP 메서드를 정하는 문제와는 별개다. 실제 작성 순서는 작업 나열 → 호출할 라이브러리의 API 확인 → 경로 함수 방식 선택이다.

1. 경로 내부에 외부 API, DB, 파일처럼 기다릴 작업이 있는지 찾는다.
2. 사용하는 라이브러리가 제공하는 호출 방법을 확인한다. 비동기 API를 사용한다면 async def와 await를 사용한다. 예: httpx.AsyncClient의 await client.get(). await가 필요한지는 함수 이름이 아니라 API의 동작과 문서로 판단한다.
3. 동기 API를 그대로 사용한다면 일반 def 경로로 시작한다. 예: httpx.Client의 client.get(). 단순히 async를 붙여도 동기 호출은 비동기로 바뀌지 않는다.
4. 기다림이 없고 가벼운 반환/검사만 한다면 async def로 작성해도 된다. 둘 다 가능하다.
5. 비동기와 느린 동기 호출을 함께 써야 한다면 동기 호출을 비동기 API로 바꾸거나, async 경로에서 await asyncio.to_thread(...) 등으로 별도 스레드에 넘긴다. 스레드에 넘기는 라이브러리와 객체의 스레드 사용 제약도 확인한다.
6. 무거운 CPU 계산은 별도 프로세스나 작업 큐로 분리한다. async/await만으로 해결하지 않는다.

기억할 기준은 비동기 I/O 도구를 선택했으면 async def + await, 동기 I/O 도구를 그대로 쓸 것이면 def다. FastAPI가 경로 함수로 실행하는 def와, async 경로 안에서 직접 호출한 일반 보조 함수는 다르다. 보조 함수에 def를 썼다는 이유로 자동 스레드 분리가 되지는 않는다.

Day_7/02/main.py는 httpx.AsyncClient를 사용하므로 fetch_todo와 이를 await하는 read_todo에 async def를 사용하는 구성이 맞다. httpx.Client로 바꾸면 두 함수를 일반 def로 작성하고 async with/await도 동기 방식에 맞게 바꾼다. 소스 변경이나 실행은 하지 않았다.
