## 답변

로그는 프로그램의 일기, 대시보드는 여러 기록을 한눈에 보는 상황판, 인터페이스는 사람이 보고 누르는 화면이다. 실시간 로그 대시보드는 프로그램에서 일어나는 일을 계속 받아 표와 숫자, 그래프로 보여주는 화면이다.

예를 들어 챗봇에서 질문을 받았는지, 답변을 만들었는지, 오류가 났는지를 기록하고 화면에 표시한다. 다음은 실제 실행 결과가 아닌 설명용 예시다.

| 시각 | 수준 | 내용 |
| --- | --- | --- |
| 10:00:01 | INFO | 질문을 받음 |
| 10:00:02 | INFO | 답변 생성 완료 |
| 10:00:05 | ERROR | 외부 서비스 연결 실패 |

INFO는 일반적인 진행 기록, WARNING은 주의할 상황, ERROR는 작업 중 오류를 뜻한다. 로그에는 비밀번호나 API 키를 넣지 않는다.

첨부 이미지에서 읽은 학습 흐름:

| 기간(2026년) | 쉬운 설명 | 대시보드와 연결 |
| --- | --- | --- |
| 10/20~10/27 | 요청을 받고 일을 처리하는 직원 만들기 | FastAPI로 로그를 받거나 조회하는 API 구성 |
| 10/28~11/03 | 기록 보관함과 출입증 만들기 | Supabase에 저장, 로그인과 접근 제어, Redis 기초 |
| 11/04~11/11 | 사람이 볼 수 있는 화면 만들기 | Streamlit의 표, 버튼, 상태 유지와 화면 갱신 학습 |
| 11/12~11/16의 보이는 일정 | 배운 내용을 합치기 | 실시간 로그 대시보드 인터페이스 프로젝트 |

이미지는 약 4주에 걸친 일정이다. 구체적인 프로젝트 평가 기준과 로그의 종류는 이미지에 없으므로 아래 설계는 학습용 제안이다.

주요 용어:

- Python: 컴퓨터에 할 일을 적는 언어. 변수, 조건문, 반복문, 함수, 리스트, 딕셔너리, 예외 처리를 익힌다.
- 백엔드: 화면 뒤에서 요청을 처리하고 데이터를 저장하는 부분.
- FastAPI: Python으로 요청 처리 창구를 만드는 도구.
- Uvicorn: FastAPI 앱을 실행하고 요청을 받을 수 있게 하는 서버.
- API: 프로그램끼리 정해진 방식으로 부탁하고 답하는 창구. 엔드포인트는 `/logs` 같은 창구 주소다.
- HTTP: 웹에서 요청과 응답을 주고받는 규칙. GET은 조회, POST는 새 데이터 제출에 흔히 사용한다.
- JSON: 프로그램끼리 데이터를 전달할 때 사용하는 글자 형식. Python 딕셔너리와 비슷해 보이지만 동일한 것은 아니다.
- Pydantic: 받은 데이터의 모양과 값이 정해진 규칙에 맞는지 검사하는 도구.
- async/await: 다른 서비스의 응답을 기다리는 동안 다른 일을 처리할 수 있도록 코드를 구성하는 방법. 모든 계산을 저절로 빠르게 만드는 기능은 아니다.
- Swagger 문서: API 설명을 읽고 요청을 시험할 수 있는 화면.
- CRUD: 만들기, 읽기, 바꾸기, 지우기. 로그의 첫 버전은 추가와 조회에 집중할 수 있다.
- GitHub PR: 코드 변경을 합치기 전에 함께 살펴보는 절차.
- SDK: 다른 서비스에 연결하기 쉽게 모아 놓은 코드 도구.
- Supabase와 DB: 기록을 저장하는 서비스와 데이터 보관함. SQL은 보관함에 저장하거나 찾아 달라고 지시하는 언어다.
- ERD: 어떤 표를 만들고 표끼리 어떻게 연결할지 그린 설계도.
- Auth/JWT: 로그인과 인증에 쓰는 기능 및 토큰 형식. 로그인 확인과 데이터 접근 권한 확인이 필요하다.
- Redis와 캐시: 자주 쓰는 자료를 빠르게 꺼내도록 임시 보관하는 용도에 사용할 수 있다.
- 세션: 사용자와 상호작용하는 동안 유지하는 상태. Streamlit의 session_state를 설정하는 것만으로 안전한 로그인 검증이 완성되지는 않는다.
- Streamlit: Python으로 표, 버튼, 그래프 같은 웹 화면을 만드는 도구.
- 멀티턴: 앞 대화를 참고하며 대화를 이어 가는 것.
- 스트리밍: 완성된 답을 한 번에 받는 대신 생성되는 부분부터 조금씩 받는 것.
- 배포: 다른 사람이 접속할 수 있는 환경에서 앱을 실행하는 것.

대시보드의 제안 구조:

`프로그램에서 사건 발생 → FastAPI가 로그를 받음 → Supabase에 저장`

`Streamlit이 FastAPI에 로그 조회 요청 → 저장된 로그 반환 → 화면 표시`

이 구조에서 FastAPI는 처리 담당, Supabase는 보관함, Streamlit은 상황판이다. Redis와 AI 요약은 첫 버전 이후 확장할 수 있다. 다만 수업에서 필수로 요구하면 포함한다.

## 만드는 순서

1. Python 딕셔너리로 로그 한 개를 만들고 리스트에 여러 개를 담는다. 필드는 id, 발생 시각, 수준, 메시지로 시작한다.
2. Streamlit에 예시 로그 10개를 표로 보여준다.
3. ERROR만 보기, 단어 검색, 오류 개수 표시를 추가한다.
4. FastAPI에 `GET /logs`를 만들고 화면에서 조회한다. 예: `GET /logs?level=ERROR&limit=50`. 이 경로와 조건은 직접 구현할 API 설계 예시다.
5. `POST /logs`로 새 로그를 받고 Pydantic으로 입력을 검사한다. Supabase에 저장하고 다시 조회한다.
6. 화면에서 2초마다 새 로그를 가져오도록 만든다. 이런 주기적 조회를 폴링이라고 한다. Streamlit의 `st.fragment(run_every="2s")`로 활성 세션에서 일정 간격으로 화면 일부를 다시 실행할 수 있다.
7. 데이터가 없을 때, 서버 연결이 끊겼을 때, 잘못된 로그를 보냈을 때를 확인한다.
8. 로그인과 접근 제어를 적용하고 배포한다. 프로젝트 요구에 따라 차트, Redis, 즉시 전달 방식 등을 확장한다.

2~3주 동안의 개인 복습 목표는 다음처럼 잡을 수 있다. 이는 첨부 수업 일정의 변경이 아닌 연습 순서다.

- 1주 차: Python 리스트·딕셔너리·함수, JSON, API 요청과 응답. 로그 목록을 반환하고 오류만 골라내기.
- 2주 차: DB 저장·조회, Streamlit 표·필터. 저장한 로그를 화면으로 가져오기.
- 3주 차: 자동 갱신, 예외 처리, 로그인, 배포. 새 로그가 생겼을 때 정한 시간 안에 표시되는지 확인하기.

첫 완성 기준은 “새 로그가 저장되면 약 2초 간격의 다음 조회 후 화면에 보이고, ERROR만 골라 볼 수 있다”로 잡을 수 있다. 실제 지연에는 요청·처리 시간도 추가된다.

## 헷갈리기 쉬운 점

- 2초마다 조회하는 것은 엄밀히는 준실시간이다. 발생 즉시 서버에서 전달하는 요구라면 SSE, WebSocket 등도 검토한다. 과제의 허용 지연과 요구 방식을 확인해야 한다.
- async/await 자체가 화면 자동 갱신을 만들어 주지는 않는다.
- 챗봇 답변 스트리밍과 로그 대시보드 갱신은 서로 다른 데이터 흐름이다.
- AI가 없어도 로그 대시보드를 만들 수 있다. 오류 요약 같은 기능에 AI를 추가할 수 있다.
- Streamlit을 쓰는 이 학습 경로에서는 HTML/CSS/JavaScript를 깊게 배우기 전에 기본 화면을 만들 수 있다.
- 새로고침할 때 같은 로그를 계속 덧붙이면 중복된다. 처음에는 최신 50개를 다시 조회해 표를 교체하는 방식으로 단순화할 수 있다.
- 이미지에는 프로젝트 세부 요구사항이 없다. 필요한 로그 종류, 갱신 속도, 필수 기술은 과제 안내에서 확인해야 한다.
